# GitHub 协作流程

GitHub 是用户、系统设计方和 Codex 之间唯一的开发交接记录。稳定规则保存在仓库文档中，具体任务保存在 Issue 中，代码结果通过 Pull Request 交付。

## 角色

- 用户：确认业务需求、决定有争议的方案、最终合并 Pull Request。
- 系统设计方：整理业务规则，创建或更新 Issue，审查 Codex 的实现与测试结果。
- Codex：读取项目文档和指定 Issue，实施代码、运行测试并提交 Pull Request。

## 信息优先级

1. 用户针对当前任务的最新明确决定；
2. 当前 Issue 的范围和验收条件；
3. 根目录 `AGENTS.md`；
4. 其余设计文档；
5. 旧 Issue、旧评论和历史实现。

遇到矛盾时不得自行猜测。Codex 应在 Issue 或 Pull Request 中列出冲突，并等待用户决定。

## 标准流程

1. 系统设计方创建一个范围明确的 Issue，写明背景、实施内容、禁止范围和验收条件。
2. Codex 阅读 `AGENTS.md`、相关文档和完整 Issue。
3. Codex 从最新 `main` 创建 `codex/issue-<编号>-<简短说明>` 分支。
4. Codex只实现该 Issue，不顺带扩展下一阶段。
5. Codex提交代码和测试，创建 Pull Request，并在说明中写入 `Closes #<编号>`。
6. Pull Request 必须列明修改文件、数据库迁移、数据安全措施、测试命令和结果、已知限制。
7. 系统设计方审查差异；修改要求以 PR review 或 Issue 评论记录。
8. Codex逐项处理意见，不能通过降低验收标准使测试通过。
9. 用户确认后合并。未合并前，下一项依赖任务不得以该分支为稳定基础。

## 状态标签

Issue 标题建议使用以下前缀：

- `[设计]`：业务或架构仍待确认。
- `[开发]`：规则已冻结，可以交给 Codex。
- `[阻塞]`：需要用户决定或补充资料。
- `[验收]`：实现已提交，等待检查。
- `[缺陷]`：已发现的错误或回归。

即使仓库暂未创建同名 GitHub Labels，也应保留标题前缀，避免状态含义丢失。

## 分支与提交

- 禁止直接提交到 `main`。
- 一个 Issue 对应一个主要分支和一个 Pull Request。
- 分支名：`codex/issue-12-batch-upload`。
- 提交信息使用动词开头并说明结果，例如 `Add resumable batch upload queue`。
- 不提交真实车辆图片、身份证件、微信聊天记录、数据库、日志、导出表或密钥。

## Issue 必填内容

- 背景与目标；
- 本次范围；
- 明确不做的内容；
- 数据与安全约束；
- 可执行的验收条件；
- 依赖项和待用户决定的问题。

## Pull Request 必填内容

- `Closes #<Issue 编号>`；
- 实现摘要；
- 关键文件；
- 数据库迁移及回滚/兼容说明；
- 测试命令及真实结果；
- 界面变化截图（如适用）；
- 已知限制；
- 未包含的后续阶段。

## 敏感数据

仓库只保存程序、测试用虚构数据和文档。真实车辆照片、车牌、VIN、车主姓名、地址、微信截图和生产数据库只能留在厂内服务器，不得提交到 GitHub。测试材料必须使用人工构造或完全脱敏的数据。
